## Closed item 1 — the lifecycle write test, and the 400 that was never the product's

The two drain tests in `pkw-shutdown.test.mjs` originally decided "in flight" with a fixed sleep,
which only makes it likely. They now arm an observation gate that numbers the requests, reports
which one entered the handler, holds exactly that one, and is released explicitly — so "the signal
arrived while the request was unfinished" is observed rather than hoped for. The chain is also
proven end to end in a dedicated test (`inflight-signal.test.mjs`): accepted → entered → committed →
response ended → signal → release → exit 0 → a fresh process reads both writes back.

The 400 that stood in the way was diagnosed rather than worked around. Both intermittent failures
had the same shape — a generic `400 PKW_REQUEST_FAILED` that names nothing — and the general form of
that shape is what closed item 5 above: the gateway maps every unclassified failure to one message,
so the first hypothesis is always "the page is broken" when the answer is usually "this fixture is
not a store the runtime can open".

* The read-back that failed inside the drain test was the test's own loopback stub answering
  `{"data":[],"success":true}` with no one-shot marker, so the sync was treated as incomplete and
  the note was left unreadable. The stub answers `{"ok":true}`; the test then passes with explicit
  signals and no sleep.
* ECONNRESET for a request parked across SIGTERM was test scaffolding: a release file created before
  the gate was armed, plus a helper reading an empty gate log, tore the connection down client-side.
  It is not reproducible with the current gate.

What is left of the older wording here is withdrawn: there is no "persistence difference specific to
that test's setup" still standing, and the fixed sleep it justified is gone. `setTimeout` in that
file now appears only in the stub's configured response delay, a readiness poll, a 5 ms yield, and
the concurrency test's 8-second race bound. Five consecutive runs: 9/9 pass, 0 fail, 0 skip, with
`PKW_TEST_DATA_ROOT` pointing at a generated fixture.

## Closed item 2 — the concurrent-starter lock test

`S3/lock two concurrent starters against one root leave exactly one writer` was flaky in two
directions: once in five full-suite runs the loser exited **4** (`UNREADABLE`) instead of **3**
(`LIVE_WRITER`), and later the loser exited **1** — indistinguishable from a crash.

One cause, in `scripts/serve-collaboration.mjs`. The pre-flight check and the gateway's atomic
`open(lockPath, 'wx')` are two steps, so two starters can both pass the check before either claims
the lock. The claim is atomic and exactly one wins, but the loser failed on a plain `Error` and
exited 1. The exit-4 flake is the same window read from the other side: the winner had created the
lockfile but not yet written its record, and an empty lockfile is `UNREADABLE`.

The process now re-asks the lock protocol after a failed claim, which is the step that was missing:
a live writer becomes `LIVE_WRITER` (3), an unreadable lockfile `UNREADABLE` (4), and the two
genuinely undecided states — the lock free, or present with no record yet — are waited through,
bounded at forty attempts of 25 ms so it can never become a silent retry loop. `refuseLock` is
shared with the pre-flight refusal, so both paths report the same shape.

Five consecutive runs of the lifecycle suite: 9/9 pass, 0 fail, `concurrent starters: running=1,
refused=1` each (`/tmp/lock-1.log` … `/tmp/lock-5.log`).

`e2e-switch.test.mjs` is the same sequence as a test on this commit, and it asserts the observations

and `verifyPrevious` only look, and the rollback acceptance and the final read-back are made of the
same recovered process the transaction started rather than a second instance the test brought up. A
child that died is a failed start with its own output, never a healthy response borrowed from
whatever else holds the port:

* the transaction **proved the stop before promoting**: `recoverySteps.stop === 'confirmed'` with
  `stopEvidence = { known: true, stopped: true, source: 'stop-hook-succeeded' }`. That proof is the
  single-writer guarantee for the promotion — a writer still holding the root would have failed the
  probe — and the rollback's own steps are asserted too: `currentRepointed`, `started`,
  `versionConfirmed` all true;
* the candidate **served** (it reported its own version, `x-pkw-version: 0.1.9-pkw.1`), the
  transaction handed exactly that release to the stop hook, and the candidate's port is free
  afterwards. A second listener still holding the port would make the restored release's start hook
  fail to bind — that is a stopped service, not a rolled-back one.
* the restored release reports its own version, reads back the note the new release wrote, and
  resolves the attachment it linked — through the API, and again on disk.
* the attachment is compared as bytes **and** as a mode, on disk and through the service. The two
  modes differ and the difference is asserted as it is: a note body is written `0o600` by the notes
  service, while attachment bytes go through `writeBytes` with no explicit mode and take the umask

scaffolding defects had to be fixed for it to be answerable at all, and both were in the
rehearsal, not the product: the seed profile's `.npmrc` pinned a one-off loopback registry that
no longer exists (every install hung on it), and the driver used the bootstrap password as the
verifier's credential (the copy's own account has its own password, which

## Closed: an upload with no filename was stored as the literal name `undefined`

Found while making the rehearsal's write acceptance honest. The audit reported `file: "undefined"`
in a read-back and it read like a reporting bug; it was not.

`web`'s `uploadAttachment` handler passed the filename through `String(args.filename)`, and
`String(undefined)` is the string `"undefined"` — so a missing name arrived at the attachments
service looking perfectly valid and was stored, indexed and served under it. The stored path is the
attachment's identity on disk, so every unnamed upload collided on one path and a reader following
the attachment got a file called `undefined`.

Both halves are fixed: `web` passes the value through as it arrived, and `attachments` refuses a name
that is absent, empty or nothing but separators — the caller is the only place that knows what the
file is called, and inventing a name would put a file in the workspace nobody can identify.

Observed, not inferred (`/tmp/dbg-upload.mjs`, against a profile built from this commit):
a named upload is stored under its name, and a nameless one is refused with
`PKW_REQUEST_FAILED`. The existing test suite is green on the change, 446 tests.

## Closed item 5 — the real-artifact E2E, and what its 400 actually was

This test had only ever been skipped: it needs a staged old artifact set, a support profile and a
pnpm store. Wired, it ran — and failed, which was the useful part. It stages the old release from
`/LlHmm9527/.pkw-deployments/0.1.7-pkw.1/packages`, stages this checkout as `0.1.9-pkw.1`, installs,
promotes, injects a post-activation verification failure after writing real content, and rolls back.
It is now **green**, and every one of its failures was in the test rather than in the code under
test. The generic 400 is what hid them:

```
e2e: space-page   expectedVersion 0.1.9-pkw.1   serving null
                  status 400  contentType application/json
                  body {"ok":false,"code":"PKW_REQUEST_FAILED","error":"操作未完成…"}
```

A loader hook (`docs/delivery/probe-gateway-error.mjs`) rewrites the gateway's one catch block in
memory, for one process, and reports the error that block is holding. Under it the page's 400 was
`DomainError: domain 'pkw': stored record 'note.created:…' in table 'commits' does not match its
schema` — a fixture defect, named instead of guessed at. Getting even that far needed one
correction of its own: the hook had been instrumenting a listener whose stderr the probe was not
draining, so after ~64 KB the listener blocked on a full pipe and stopped answering. Each finding
below was then confirmed by the error the hook named, not by inference.

**The fixture was not a store the runtime can open** (`scripts/tests/helpers/synthetic.mjs`), in
four independent ways:

* the note file carried no frontmatter, so the runtime could not read its own note identity back out
  of the file and reported the note as missing;
* the note lived at `synthetic/note.md`, while a note path is workspace-relative and resolves as
  `<workspace>/notes/<relativePath>`;
* the `u_pkw_commits` row held three of the six fields `OperationCommit` requires — and the domain
  facility rejects a record it cannot parse rather than skipping it, which is why one bad row took
  the whole page down;
* the attachment row used invented field names (`title`/`contentHash`/`revision`) instead of the
  product's `AttachmentRecord` (`filename`/`sha256`/`sizeBytes`/`observedRevision`/`indexedAt`/
  `indexable`).

Every shape now comes from a store the product itself wrote. Verified against the product's own
listener: login `200`, space page `200` with the version header, `listNotes` `200`, `getNote` `200`,
and **no error reaches the gateway catch at all**.

**The test itself was wrong in five more places**, each of which had been concealed by the first
failure:

* the old release's profile was assembled from its ten tarballs alone. A release profile is its
  packages *and* the Harness peers it declares, so the restored release could not boot at all
  (`ERR_MODULE_NOT_FOUND`) — the rollback was rolling back to a release that was never runnable,
  and "the old release still runs" was an assumption. The peers are now staged as a tree from their
  own packed contents and laid into the profile beside its own packages; only the peers move, so an
  old package is never overwritten by a peer's newer copy;
* it asserted on `<workspace>/notes/rollback-X.md` while `createNote` was given
  `notes/rollback-X.md`, which the runtime resolves to `<workspace>/notes/notes/rollback-X.md`;
* it asserted the note file mode was `0o644`; the product writes `0o600`, and the store the live
  site serves from carries `0o600` on every note;
* it uploaded the attachment as multipart form data, which `/api` does not accept: the upload was
  refused, `attachmentId` stayed null, and "the rollback carries an attachment" was never tested at
  all. It is uploaded as base64 JSON and then linked from the note body — `getNote` reports the
  attachments a note *references*, scanning the markdown for managed link targets, not what happens
  to share an owner id;
* it demanded the rollback status `rolled-back` while supplying no `verifyPrevious` hook, so the
  transaction was right to record `rolled-back-unverified`. The hook now supplies the observation —
  an authenticated session on the restored release reporting the restored version — instead of the
  test asserting a status its own evidence could not support.

5. **Switch.** `deploy/switch-release.mjs --root … --version … --artifact-dir … --support-dir …
   --stop-hook … --managed-unit <unit> --start-hook … --verify-hook … --reachable-url …
   --public-origin … --expected-version …`. The transaction stops and proves the stop, snapshots

6. **Accept.** The verifier is enforcing: login, serving version, note read-back. Reachability alone

7. **Watch.** After acceptance, check the unit's `NRestarts`, the lock's owner, and one read through

## Rollback

Two levels, and the first is the one the transaction already does by itself:

* **Automatic.** A failed start, a failed acceptance, or a drift refusal restores the previous
  release inside the same transaction: stop the candidate (probe-confirmed), write the snapshot's
  inputs back only if they changed, repoint `current` atomically, start the old release, verify it.
  The result is `rolled-back` or `rolled-back-unverified`, and the original error is preserved.
* **Manual.** Point `current` back at the previous release directory and start the unit — but only
  after stopping the candidate and confirming it stopped, exactly as the transaction does. The
  previous release tree is never deleted by a switch, so this needs no restore step.

Never delete recovery material (snapshots, backups, preserved copies) before a rollback has been
verified. A preserved copy that failed the isolation gate is re-verified before it is reused, and
refused again if it still fails — that path is covered by tests.
